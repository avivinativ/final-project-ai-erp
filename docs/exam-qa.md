# שאלות צפויות במבחן/הגנה

**איך נמנעים מהתנגשות מספרי חשבוניות כששתי חשבוניות נוצרות באותה דקה?**
המספר מבוסס timestamp ברזולוציית דקה (`INV-YYYYMMDDHHmm`), לא מונה רץ. שתי חשבוניות שנוצרות
באותה דקה בדיוק כן יקבלו אותו מספר — זו מגבלה ידועה (ראו known limitations), אבל בפועל
WF1 עצמו רץ ברזולוציית דקה כך שהסיכוי נמוך, ואין תלות ב"זיכרון" חיצוני של מונה שיכול
להתאפס/להתנגש כמו במונה רץ קלאסי.

**איך מזהים כפילות ליד?**
WF3 מחפש ב-Airtable את כל הרשומות עם אותו Email (כולל הרשומה החדשה עצמה), וסופר. אם יש
יותר מהתאמה אחת — Status=Duplicate. אחרת — New.
(תוקן ב-2026-09-22: המימוש המקורי השתמש ב-node מסוג Summarize שקיבץ items מכל ה-batch יחד,
מה שגרם לתקלה אמיתית כששני לידים ומעלה נוצרו באותה דקה — כל ה-batch קיבל את אותה תוצאת ספירה
במקום ספירה פר-ליד. הוחלף ב-Code node שסופר לפי `pairedItem` ומחזיר תוצאה נפרדת לכל ליד.)

**מה קורה אם ה-vector store מתאפס?**
הוא חי בזיכרון של תהליך n8n. כל restart (כולל deploy מחדש של הקונטיינר) מאפס אותו. חובה
להריץ שוב WF6 ואז WF7 ידנית (Execute workflow) לפני כל דמו/שימוש.

**איך המערכת מטפלת בשגיאות?**
לכל 10 ה-workflows מוגדר WF0 כ-Error Workflow. כל כשל (בכל node, בכל workflow) מפעיל את WF0,
שמזהה את שם ה-workflow, ה-node שנכשל, הודעת השגיאה וקישור להרצה — ושולח הכל כהודעת Telegram
לבעל העסק.

**למה WF4a (מיילים קרים) כבוי כברירת מחדל?**
כי הוא שולח מיילים אמיתיים ללידים אמיתיים על בסיס Schedule (כל 3 שעות) ללא אישור אנושי בכל
פעם. הפעלתו היא החלטה מודעת של בעל העסק, לא ברירת מחדל טכנית.

**איך בוט המנהל יודע שזה באמת המנהל?**
ה-node "האם זה המנהל" משווה את `chat.id` שמגיע מטלגרם לערך קבוע (chat id של בעל העסק). כל
מי שאינו זה לא מקבל תשובה מהסוכן.

**איך הסוכנים נמנעים מהמצאת מידע (הזיה)?**
ה-system prompt של כל סוכן RAG (WF5, WF13) מנחה אותו להשתמש אך ורק בכלי החיפוש (SearchPolicies,
SearchProducts) ולא להמציא מידע. סוכן המנהל (WF9) מקבל את כל נתוני החשבוניות כטקסט בפרומפט
ומונחה לענות רק על בסיסם, ללא כלים נוספים.

**האפליקציה כותבת ישירות ל-Airtable?**
רק לקריאה (Server Components קוראים ישירות מ-Airtable REST API עם PAT בצד השרת בלבד). כל כתיבה
(ליד/משימה/חשבונית/צ'אט) עוברת אך ורק דרך ה-webhook היחיד של WF13 — ה-PAT אף פעם לא מגיע לדפדפן.

**מה קורה בפעולת webhook לא מוכרת?**
ה-Switch node ב-WF13 מנתב פעולות לא מזוהות לתשובת שגיאה מובנית (HTTP 400, `{ok:false, error:"unknown action"}`).
